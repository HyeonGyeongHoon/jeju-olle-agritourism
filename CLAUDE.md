# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

제주올레 도슨트 (Jeju Olle Docent) — a LangGraph-based RAG agent that turns a free-form natural-language query (visit timing/crop/region/theme) into a structured **B2B tourism-product proposal document** (기획서) for Jeju Olle trail courses: a spec/Market-Insight section, a timeline table with crop/harvest-season narration, a local-partnership ideas section, a climate-risk/Plan-B section, and a trust-tagging footer. Backed by Supabase (Postgres + pgvector), served over FastAPI SSE streaming. (The project pivoted from an earlier B2C chatbot design — see `docs/retrospectives/` for that history — so older code comments/docs may still describe the B2C framing; this file reflects the current B2B state.)

Required `.env` keys actually read by the code: `SUPABASE_URL`, `SUPABASE_KEY`, `UPSTAGE_API_KEY` (Solar chat + embeddings), `VISIT_JEJU_API_KEY`. There is no KMA/weather API key — `weather_client.py` is 100% local (static seasonal table + keyword simulator), not a real KMA call; don't add a `KMA_API_KEY` requirement back without actually wiring a real weather call. `.env.example` also lists `REPORT_API_KEY` (optional — see below), so it's these five keys, nothing else.

`REPORT_API_KEY` (optional): if set, `POST /api/v1/report/generate` (`src/main.py`) requires a matching `X-API-Key` header (checked with `secrets.compare_digest`); if unset, the endpoint accepts unauthenticated requests (fine for local dev, but leaves the endpoint open to unlimited paid Upstage API calls — set this in any environment reachable by untrusted clients). The endpoint also applies a simple in-memory sliding-window rate limit (5 requests/60s per API key, or per client IP when no key is presented) — single-process only, does not coordinate across multiple `uvicorn` workers/processes.

## Architecture

### LangGraph pipeline (`src/agent/`)

Entry point `agent_runtime` is built in `graph.py` and consumed by `src/main.py`'s SSE endpoint via `agent_runtime.stream(inputs)`. Fixed-path graph (11 nodes) with four intent-based conditional branches (a fourth, `route_after_retriever`, was added 2026-07-25 for the fail-fast exit described below):

```
intent_classifier → intent_parser → market_location_resolver ─┬─(non-recommendation)─────→ quick_responder ────────────────────────────────┐
                                                            └─(course_recommendation)→ safety_evaluator → retriever ─┬─(is_exit_early)──────┤
                                                                                                                       └─(normal)→ report_generator ┤
                                                                                                                                                     └→ quality_checker ─┬─(passed / loop_count≥3)─→ END
                                                                                                                                                                          └─(failed)─→ query_rewriter ─┬─(non-recommendation)→ tool_agent
                                                                                                                                                                                                            └─(course_recommendation)→ retriever (loop, max 3x)
tool_agent ⇄ tool_executor (function-calling loop, max depth 3)
```

`retriever`'s `is_exit_early` branch (`route_after_retriever` in `graph.py`) joins the same `quick_responder` node the non-recommendation intents use — see the `retriever`/`quick_responder` bullets below for what actually flows through that shared node in each case.

- **`intent_classifier`** (`classify_intent_node` → `router.py`'s `route_intent`): classifies the query into 3 categories — `course_recommendation` / `info_lookup` / `other`. **(2026-07-26 consolidated from 5 categories down to 3)** the earlier `course_info` and `olle_general_info` categories were merged into `info_lookup`, with no legacy alias kept (`IntentCategory` in `src/models/schema.py` now has exactly these 3 members). This was a router-layer-only cleanup: every routing/node consumer in `graph.py`/`nodes.py`/`main.py` had already only ever branched on `== course_recommendation` or `== other` (or `!=`) — nothing in the codebase branched on `course_info`/`olle_general_info`/`info_lookup` individually, since all three collapsed onto the same `quick_responder` → `tool_agent` pipeline anyway — so downstream logic is unchanged; only `router.py`'s classification values and `SYSTEM_PROMPT` category descriptions moved. Where the categories' old names appear below (e.g. in dated bullets describing what a rule returned *at the time*), they're kept for continuity with the commit history/retrospectives rather than silently rewritten — see `docs/retrospectives/` for that history. Only attaches a label to `intent_category` — actual branching is done by `route_after_location_resolve` in `graph.py`. `course_recommendation` is the only intent that proceeds to the full pipeline (safety → retriever → `report_generator`); the other two (`info_lookup`/`other`) route to `quick_responder`.
  - `route_intent` is **two-stage** (2026-07-25): a rule-based precheck (`_rule_based_precheck`, **no LLM call**) runs first and settles three classes of query deterministically; only what it doesn't match falls through to the Solar LLM classification. (a) A **plain course-recommendation ask** — contains "코스"/"올레" + "추천", no 기획서/기획안/기획해/상품 기획/상품화 keyword, and no specific course named — is forced to `other`, because this service does not recommend individual courses and LLM classification was observed flip-flopping between `other` and `course_recommendation` across runs of the identical query. (b) Profanity, and 1–2-word greetings, are forced to `other`. (c) A query that **already names a specific course** *and* says "추천" (with no 기획서 keyword) is forced to **`info_lookup` (당시 이름 `course_info`, merged 2026-07-26), not a refusal** — "7코스 초보자한테 추천할 만해?" is an opinion/suitability question about that one course, not a request to pick a course — and `target_course` is filled from the regex at the same time. Don't "fix" (c) back into a refusal: over-refusing exactly this shape is the bug that motivated the whole precheck.
  - Course naming is detected by `_SPECIFIC_COURSE_PATTERN` (digits + optional `-digit`/`-letter` + optional "번" + "코스", so "1번 코스"/"10-1 코스" spellings match too) and normalized by `_normalize_course_name` to the DB `course_name` form (`1코스`/`10-1코스`/`3-A코스`) — that normalization is load-bearing because downstream `_filter_course_ids_by_target_course` compares with `==`. A course name that appears **only behind an exclusion marker** (말고/빼고/외에/이외/제외/아닌/아니고/대신 within 8 chars after the match, e.g. "1코스 말고 다른 코스 추천해줘") does not count as naming a course, so that query is still refused as (a).
  - The router prompt's `info_lookup` category (`src/agent/prompts/router.md:11`, 3rd of 3; absorbed the former `course_info`/`olle_general_info` split as sub-cases 3-a/3-b/3-c on 2026-07-26) covers **both** metadata lookups (3-a: distance/difficulty/time/start-end/stamps) **and** opinion/evaluation/suitability questions about an already-named course (3-b), plus general olle-trail info/culture/crop/visitor-stats lookups (3-c) — the metadata+opinion half is what makes the LLM classify "1코스 어때?" (no "추천" token, so the rule in (c) doesn't fire) as `info_lookup` instead of `course_recommendation`. When the LLM returns `target_course` as null (observed live, reproducible 3/3), `route_intent` backfills it from the same regex; an LLM-supplied value wins.
  - **(d) added 2026-07-26)** A query with `has_course_ref` (코스/올레) + `has_proposal_ask` (기획서/기획안/기획해/상품 기획/상품화) but **no** "추천" token and no specific course named — e.g. "당근 코스 기획서 써줘", "올레 코스로 상품 기획해줘" — is now forced deterministically to `course_recommendation`, no LLM call. Found live while verifying the `strict_single_crop` feature below: this exact query shape used to fall through to the 2-stage LLM classification (nothing in (a)/(b)/(c) matched it) and that LLM call was observed flip-flopping `course_recommendation`/`other` across identical repeated calls (3 runs: 2× wrongly `other`) — the same class of nondeterminism (a)'s "코스+추천" rule was already built to eliminate, just on a different keyword combination ("기획서" without "추천" instead of "추천" without "기획서"). Deliberately scoped narrow: a query where `has_recommend_ask` is *also* true ("당근 코스 추천해서 기획서 만들어줘") or where a specific course is named ("1코스로 기획서 만들어줘") still falls through to the LLM path unchanged — neither combination had an observed nondeterminism report, so their existing behavior (which tests already assumed) was left alone rather than folded into the new rule speculatively. See `_RULE_BASED_REASON["proposal_without_recommend_word"]` and the guard at `router.py:133`.
- **`intent_parser`**: separate LLM call that extracts RAG search filters into `B2BQueryParams` (`hard_constraints.wheelchair_required`, `hard_constraints.max_time_hours`/`max_distance_km`/`allowed_difficulties` (the 2026-07-27 detail constraints — see the `retriever` bullet, and the open gap in the gotchas about this node's parse-failure fallback silently dropping them), `vector_query`, `target_month`/`season`, `key_item_or_crop`, `preferred_location`, `concept_theme`, `target_audience`, `include_market_insights`, `strict_single_crop`). There is no `soft_constraints` (time/distance/difficulty) any more — that B2C-era relaxation mechanism was removed; the RDB filter is now hard-constraints-only, single pass, no fallback tiers. When the query names a region by a **visitor-statistic condition** instead of a place name (e.g. "외국인 관광객이 많았던 지역"), `preferred_location` is left null and `market_location_query` (metric/year/month/direction) is filled instead. Not the same thing as `intent_classifier` — don’t confuse the two. Note that its prompt tells it to fill `preferred_location` when a "지역/코스명" is named directly, so it does in practice put a **course name** into that region field ("1코스 괜찮을지 추천해줄래?" → `preferred_location='1코스'`, confirmed live 2026-07-25); both consumers (`quick_responder`, `retriever`) therefore null it out via `_looks_like_course_name` before using it as a region — see those bullets.
  - **`strict_single_crop` (bool, added 2026-07-26)**: true only when the query uses an explicit exclusive-single-crop phrasing — "당근**만**", "**오직** 마늘만을 활용한", "감귤**만**을 활용한" — via `src/agent/prompts/parse_intent.md` rule 11; a plain crop mention with no exclusivity marker ("당근 코스 기획서 써줘") stays `false`, which is a deliberately-confirmed behavior: an unmarked crop mention must still expose the course's full crop set (this is not a bug to "fix" toward stricter filtering). Defaults to `False` on LLM-parse failure — this field is a scope preference, not a safety hard-constraint, so unlike `wheelchair_required` it needs no separate keyword re-check on the fallback path. Consumed only by `report_generator` (see below); `retriever`'s RDB filtering does not read it.
- **`market_location_resolver`**: only runs when `market_location_query.metric` is set. Resolves the natural-language statistic condition to an actual region by querying `visitor_analytics` (via the Supabase query builder — `metric` is restricted to the `MarketLocationMetric` enum, so no SQL-injection path exists), restricted to administrative dongs that Olle courses actually pass through (`_get_olle_relevant_admin_dongs`, using `data/jeju_districts.csv` + a hardcoded 법정동→행정동 map for the urban "동" areas the CSV doesn’t disambiguate — see `_LEGAL_DONG_TO_ADMIN_DONG`; both it and `_get_olle_relevant_admin_dongs` moved to `src/services/db_service.py` on 2026-07-26). Writes the resolved region into `b2b_params.preferred_location` (and `market_location_resolution` for citing the reason later) so every downstream node treats it exactly like a directly-named region. Runs for both branches (`quick_responder` and the full pipeline) before the fork, since `quick_responder` also needs `preferred_location`/`market_location_query` resolved.
- **`quick_responder`** (`quick_responder_node`): handles all intents except `course_recommendation`, **plus** the new `is_exit_early` fail-fast rejection from `retriever` (see above) — answers requests for Jeju culture/crop knowledge or visitor-statistics *information itself* (not a report) with a short prose answer instead of the 5-section 기획서 format. Searches `culture_crop_knowledge` via the shared `_search_culture_knowledge` helper (also used by `retriever`) and `visitor_analytics` via the shared `_fetch_market_insight`, but does **not** touch `retrieved_chunks` (no course search) — that empty state is itself the signal `check_quality_node` uses to pick its chunk-less verification branch. Feeds into `tool_agent`.
  - **`is_exit_early` short-circuits first** (2026-07-25, checked before even `get_supabase_client()`, so ahead of the `other` check below): if `retriever` set the fail-fast flag, this node returns `exit_reason` verbatim (wrapped as `"요청하신 조건으로는 기획서를 작성할 수 없습니다. {reason}"`, matching `generate_report_node`'s older `if not chunks:` phrasing) as both `docent_answer` and `final_response`, with **no DB search at all**. This is a different case from the `other` intent below — here `intent_category` is still `course_recommendation`, it just didn't reach `report_generator`.
  - `intent_category == other` short-circuits at the top of the node: it returns `_OUT_OF_SCOPE_DECLINE_MSG` as both `docent_answer` and `final_response` **without searching anything**. Two very different queries land in `other` — totally unrelated ones ("제주도 날씨 어때?", "서울 맛집 추천해줘") and on-topic-but-refused course-recommendation asks ("당근 코스 추천해줘") — and neither should get a culture/statistics answer substituted for the refusal. The message text itself (2026-07-25, revised) is deliberately phrased as a generic "this question is out of scope, here's what the service actually does" statement rather than one anchored to "course recommendation" specifically — an earlier wording that opened with "이 서비스는 개별 코스를 추천해 드리지 않고..." read oddly for a totally unrelated query like a weather question, since it answered a refusal the user never asked for.
  - When `target_course` is set, `_fetch_course_meta_by_name` pulls that course's real DB row (`crops`, `administrative_areas`, plus the measured `total_distance_km`/`estimated_time_hours`/`estimated_time_text`/`difficulty`/`start_point`/`end_point`) into the new `course_meta` state field, and `_build_course_meta_context_str` injects those figures into the prompt as the *only* permitted basis for difficulty/suitability claims. Without the measured columns the LLM asserted things like "7코스는 비교적 평탄해 초보자도 좋다" out of thin air (the real 7코스 is 17.6km / 5–6h / difficulty 중) — verified live 2026-07-25. Fields with no value are omitted from the prompt rather than sent empty, and the prompt forbids adding terrain/stamina judgments that aren't in the data or recommending a different course/region.
  - Region-field pollution guard: `preferred_location` is nulled when `_looks_like_course_name` says the whole value is a course name (reuses `router.py`'s `_SPECIFIC_COURSE_PATTERN`), *then* backfilled from `course_meta.administrative_areas` via `_resolve_stats_region_from_areas`, which converts 법정리/법정동 → 행정동 through `_LEGAL_DONG_TO_ADMIN_DONG` and only accepts a candidate that `_get_olle_relevant_admin_dongs` confirms — **fail-closed to `None`** if nothing converts, since passing an unverified region is worse than passing none. The corrected `key_item_or_crop`/`preferred_location` are written **back into `state["b2b_params"]`**, not just held in locals: `tool_agent_node` reads `b2b_params` itself to decide tool calls, so a local-only fix left it calling the statistics tool with `region_dong='1코스'`, whose "조회 가능한 지역: ..." error list the LLM then surfaced as "대신 이 지역들을 추천드릴 수 있어요" — reintroducing the very other-course/region recommendation the routing rules exist to prevent.
  - `_fetch_market_insight`'s `target_month=None` handling changed 2026-07-25: it used to return `None` outright whenever the query didn't name a month, and this node fed it `target_month` after that field had already been defaulted to *today's* month — so "OO동 최근 방문객 수는?" (no month named) silently failed whenever `visitor_analytics` wasn't yet ingested through the current calendar month (confirmed live: DB ingested only through 2026-05, query ran on 2026-07-25), producing a wrong "통계를 찾지 못했습니다" answer plus 5–6 wasted `quality_checker` retry cycles. Fixed on both ends: `_fetch_market_insight` now returns that region's single most-recent row, unfiltered by month, when `target_month` is `None` (rather than failing), and this node now passes it the query's *actual* stated month (`b2b_params.get("target_month")`, `None` if unstated) instead of the already-defaulted-to-today value — the separate `target_month` used for crop-seasonality narration elsewhere in this node is untouched, since that's a different consumer of the same field name and defaulting it to today is correct there.
  - `_fetch_market_insight`'s region-name matching was also fixed 2026-07-25 (found live while re-verifying the `eup_myeon_dong_areas` fix above): it did `.eq("region_dong", region_dong)` — exact match only — while `_filter_course_ids_by_location` had just been made tolerant of suffix-omitted region names ("한림" matching "한림읍"), so a query like "한림 기획서 만들어줘" matched the right courses but Market Insight silently came up empty even though the 한림읍 row actually exists in `visitor_analytics`. Fixed by adding `_resolve_canonical_region_dong`, which only runs as a fallback when the exact-match query returns nothing: it fetches the distinct `region_dong` values and finds one whose suffix-normalized form (via the same `_normalize_admin_tier_name` helper `_filter_course_ids_by_location` uses) matches the input, then re-queries with that canonical name. Fails closed to `None` if the normalized match is ambiguous (not currently possible — all 43 `region_dong` values are suffix-unique) rather than guessing, since Market Insight numbers are quoted verbatim in the report. The normal (exact-match) path costs no extra query.
  - **Culture-knowledge search is now skipped entirely when the query has no crop/theme signal (2026-07-27).** `_search_culture_knowledge(client, key_item_or_crop, fallback_query)` falls back to embedding the raw query text (`fallback_query`) whenever `key_item_or_crop` is `None`, at a low 0.1 similarity threshold — so a pure statistics query like "구좌읍 최근 방문객 수는?" could still pull back unrelated crop/culture docs (e.g. 유채꽃/양파) purely off incidental text similarity. This node now computes `should_search_culture = bool(key_item_or_crop) or bool(b2b_params.get("concept_theme"))` (evaluated *after* the `target_course` → `course_meta.crops` auto-fill above, so a named course still triggers the search) and only calls `_search_culture_knowledge` when that's true; otherwise `culture_chunks` is `[]` with no DB/embedding call at all. When skipped, the `[문화·작물 지식 검색 결과]` block is dropped from the LLM prompt entirely (`culture_section = ""`) rather than filled with a "찾지 못했습니다" placeholder — deliberately, since stating a search failed when it was never attempted tends to make the LLM add an unwarranted aside about it. `quick_responder.md` gained absolute rule 8 telling the LLM that when that section is absent, answer from Market Insight alone in one paragraph and don't invent any crop/culture content. Regression tests: `tests/test_quick_responder_node.py::test_quick_responder_node_skips_culture_search_when_no_crop_or_theme` / `::test_quick_responder_node_runs_culture_search_when_only_concept_theme_present` (the latter guards that a `concept_theme`-only query, e.g. "힐링" with no crop, still searches). Verified by unit test only, per user decision — the live path would cost real Upstage API calls (Gate B) for a change already covered by direct calls mirroring the real `_search_culture_knowledge` signature.
- **`safety_evaluator`**: **no real weather API involved** — combines a static per-month seasonal-climate table (`get_seasonal_climate_note`) with an LLM-based judgment call, `assess_weather_risk_from_query` (`weather_client.py`, reuses the Solar chat API — no new external integration). Only its **DANGER** verdict is allowed to override the seasonal reading. Until 2026-07-24 this was a naive substring match (`"태풍" in query`, etc.) that misfired on any query merely *mentioning* a weather-risk word — e.g. "작년 태풍 피해가 컸나요?" (a question about the past) triggered the same forced reroute as an actual "is it safe to go now" question. It's now a Solar LLM call classifying whether the query is really about a current/near-term risk to *this* visit, vs. a historical/hypothetical/advice-seeking mention; on LLM failure it fails closed to **SAFE** (not DANGER — the whole point of this function is eliminating false-positive reroutes, so failing to DANGER would just reintroduce the same problem under a different trigger). (There is no `get_current_weather` function and no `KMA_API_KEY` — don’t assume a live KMA call is happening here; this is still not a real weather API, just a smarter query-classifier than plain substring matching.)

### SSE streaming (`src/main.py`)

`report_event_generator` (endpoint: `POST /api/v1/report/generate`) runs the graph in a background thread (`loop.run_in_executor`) and streams events **live** as each node actually completes, via an `asyncio.Queue` the background thread pushes into with `call_soon_threadsafe` — it does not wait for the whole graph to finish first. Per node completion it emits `event: node_progress` (`{node, label}`, label text from `NODE_PROGRESS_LABELS`); once some node has set `final_response` (usually `report_generator` on the course_recommendation path, or `tool_agent` on the other two intents' (`info_lookup`/`other`) path), the queue drains and it emits one `event: report` (the complete Markdown 기획서, not token-by-token) followed by `event: end`. On exception, `event: error` instead. There is no typing-effect/token-pacing simulation — that belonged to an earlier, now-deleted `/chat/stream` endpoint.

If the client disconnects mid-stream (closed tab, etc.), Starlette throws `GeneratorExit`/`CancelledError` into `report_event_generator` at its `await queue.get()` suspension point; a `finally: cancel_event.set()` there signals the background thread (via `_stream_until_cancelled`, checked before consuming each node's result from `agent_runtime.stream()`) to stop advancing to further nodes. This can't interrupt an already-in-flight `requests.post` inside the current node, but it does stop a query-rewriter retry loop from burning through its remaining paid API calls after nobody is listening anymore.

`node_output = event[node_name] or {}` — the `or {}` is load-bearing, not defensive-programming boilerplate. If a graph node returns an empty dict `{}` (no state keys changed — `market_location_resolver` does this whenever there's no statistic-based location condition, which is the common case), LangGraph's `stream()` surfaces that step's event value as `None`, not `{}`. Without the guard, `node_output.get("final_response")` throws `AttributeError: 'NoneType' object has no attribute 'get'` and the whole SSE response dies mid-stream (confirmed in production 2026-07-24, reachable from a plain course-recommendation query with no location/crop condition). Any new node you add that can legitimately return `{}` needs this same awareness downstream.

### Nodes package (`src/agent/nodes/`)

**Added 2026-07-26 as a third pure refactor that same day — no behavior change.** The 1860-line `src/agent/nodes.py` was split into a 6-submodule package; **the file `src/agent/nodes.py` no longer exists**. See the submodule table in the LangGraph-pipeline section above for what went where. Nothing about routing, prompts, query semantics, or the price formula changed.

- **Import compatibility is a contract, not a convenience.** Before the split, the node functions *and* every helper/client they use (`get_chat_completion`, `get_supabase_client`, `_fetch_market_insight`, …) were all globals of one module, so callers wrote `from src.agent.nodes import X` and tests wrote `patch.object(nodes, "X")`. `nodes/__init__.py` re-exports all of those names (`__all__` — 59 as of 2026-07-27) to keep that namespace byte-identical. Don't remove a name from `__all__` because it "looks unused" — it's likely a mock target or a cross-submodule reference.
- **Local-import convention (the load-bearing design decision).** When a submodule needs one of those shared names, it imports it **inside the function body** (`from src.agent.nodes import X`, i.e. through the package `__init__`), *not* at module top level. Each submodule carries a "로컬 임포트 규약" comment saying so. Because the name is resolved at **call time** against the package attribute, `patch.object(nodes, "X")` swaps the object the running node actually uses. A top-level `from ... import X` in each submodule would have bound the original at import time and silently defeated every existing mock. There were 12 such call sites as of 2026-07-26 (intent 3, quality 2, reporter 2, retriever 3, safety 1, tools 1); 2026-07-27's time/distance/difficulty hard-constraint work added two more, both in `retriever.py` — `_describe_target_course_mismatch` and `_describe_hard_constraint_zero_match` each import `_normalize_allowed_difficulties` (the local import was `_DIFFICULTY_ORDER` when the field was still `max_difficulty`, changed with the `allowed_difficulties` replacement) — making the total **14** and retriever's count 5.
- **Consequence — `patch.object(nodes, X)` works again without exception.** All 290 tests passed with **zero test-file edits**, in deliberate contrast to the `db_service.py` extraction earlier the same day, which broke 7 tests. The two cases are genuinely different and both rules are live:
  - *Between node submodules* (e.g. `quality.py` calling `reporter.py`'s `_build_culture_context_str`, or any node calling `get_chat_completion`): the local-import convention routes the lookup through `src.agent.nodes`, so **patching `nodes` is correct and sufficient**.
  - *Between helpers inside `db_service`* (e.g. `_resolve_stats_region_from_areas` → `_get_olle_relevant_admin_dongs`): still **not** interceptable via `nodes`; patch `src.services.db_service`. The nodes split did nothing to change this.
  - The verification for this was a mock-injection script proving 12/12 local-import sites are actually intercepted — not merely "the suite is green", since a green suite can also mean the mock was never reached.

## Known environment gotchas

- Supabase table/RPC DDL in `supabase/schema.sql` is never auto-applied — there is no raw-SQL execution channel via the REST client, so each new section (e.g. the 8-1 `culture_crop_knowledge` ALTER, or the `visitor_analytics` DDL) must be run by hand in the Supabase SQL editor before the corresponding ingestion script will work. Don't assume a table exists just because its `CREATE TABLE` has been sitting in this file for a while.
- `ruff check .` is **not** clean on this repo: it reports a nonzero and slowly growing number of `E501` (line-too-long) findings, because `pyproject.toml` sets `line-length = 88` with `select = ["E", "F", "I"]` and `ignore = []`, while the house style writes long explanatory Korean comments. So Gate C's `ruff check .` will not come back empty on this repo — recent sessions have compared against the previous E501 count and treated "no new error *categories*" as the bar, but that reading has never been confirmed with the user, so ask rather than assume when a change adds E501s. (Current reference point for that comparison: **1506 findings as of 2026-07-27, in four categories** — E501 1475 / I001 16 / F401 8 / E402 7. Earlier the same day it read 1340, then 1370, then 1413→1486 across that day's feature work; the historical `F541`/`F841` findings are gone, so treat four categories, not six, as today's baseline shape. When asked on 2026-07-27 about +25 new E501s that were all Korean docstring lines in `state.py`, the user chose to accept them uncompressed. Note the count is inflated by ruff measuring East Asian characters as width 2, so many flagged Korean lines are under 88 actual characters.) Whichever way it goes, the fix for the noise is a deliberate decision about `line-length`/`ignore`, not reflowing every Korean comment.
- **(Resolved 2026-07-27) Prompt-instruction leakage into user-facing output** — a recurring cosmetic class (no wrong facts) that had sat open since 2026-07-25/26. All three known instances were root-caused and fixed on 2026-07-27; each now has a regression test, and a 10-run live sweep found **zero** violations. The root causes turned out to be three *different* mechanisms, not one shared prompt-hygiene weakness, which is why they're kept listed separately:
  - **`tool_agent_node`'s internal `[주의]` instruction leaking verbatim (fixed 2026-07-27).** The label itself was the bug: `nodes/tools.py` prefixed the "don't recommend a different course/region" directive with a bare `[주의]`, and `tool_agent.md`'s absolute-rule 2 then *named that label* ("`[주의]` 지시를 우선하세요"), so the LLM read `[주의]` as a user-facing warning banner it was supposed to reproduce — answers came back containing "[주의] 이 질문은 특정 코스에 대한 것이므로…". Live-verified on 3 `target_course` queries: no `[주의]`/`내부 지시`/`[대상 코스]` in any answer, **and the policy itself still held** — "1코스 2019년 3월 방문객 수 알려줘" (period not in the DB) answered "확인할 수 없습니다…" without degrading into recommending a different region. **Domain logic rules** (same source, also summarized in the Architecture section above):
- Hard constraints (e.g. wheelchair access) are never relaxed. There is no B2C-era soft-constraint relaxation any more (time/distance/difficulty fallback tiers — intentionally removed). Don't reintroduce that without discussing it first — it was a deliberate cleanup, not an oversight. **This is not the same thing as the 2026-07-27 addition of `max_time_hours`/`max_distance_km`/`allowed_difficulties` to `hard_constraints`** — those are a *new*, never-relaxed hard constraint (product requirement: reject immediately when the requested time/distance/difficulty combination excludes every course in the DB, rather than silently generating a report for a mismatched course), not a revival of the removed B2C fallback-tier mechanism. One deliberate fail-**soft** exception inside this otherwise fail-fast mechanism: an `allowed_difficulties` value the LLM invented that isn't one of `"하"`/`"중"`/`"상"` is dropped rather than enforced (`_normalize_allowed_difficulties`) — rejecting a user over a condition they never stated is worse than ignoring a malformed one. See the `retriever` bullet in the Architecture section for the full mechanics.
