# Jeju Docs Sync

jeju-olle-docent는 세션마다 아키텍처가 빠르게 바뀌어왔고(B2C→B2B 피봇, 노드 여러 차례 개명/병합),
문서가 코드보다 뒤처지는 stale-doc 문제가 반복적으로 발생한 프로젝트다. 이 스킬은 각 문서를
"어떻게" 갱신해야 하는지, 특히 언제 다시 쓰면 안 되는지를 정리한다.

## 문서 지도

| 문서 | git 추적 | 로딩 시점 | 성격 |
|---|---|---|---|
| `CLAUDE.md` | **추적됨** | 매 세션 자동 | 현재 아키텍처의 사실 진술. 틀리면 다음 세션이 잘못된 전제로 작업함 |
| `docs/project_architecture.md` | 비추적 | 요청 시 | 노드 테이블(현재 상태) + 하단 날짜별 변경 이력(과거 기록) |
| `docs/project_guidebook.md` | 비추적 | 요청 시 | 온보딩용, 디렉토리 구조·패턴·데이터 흐름 |
| `docs/agent_prompt_workflow.md` | 비추적 | 요청 시 | 노드별 실제 시스템 프롬프트 명세 |
| `docs/qa_test_scenarios.md` | 비추적 | 요청 시 | 수동 QA 시나리오 + 라이브 실행 결과 로그 |
| `docs/retrospectives/{YYYY-MM-DD}.md` | 비추적 | 요청 시 | 그날의 작업 회고 |

git 추적 여부가 중요한 이유: `docs/`는 `.gitignore` 대상이라 커밋해도 반영되지 않는다.
`CLAUDE.md`를 수정했다면 그건 커밋 대상이라는 걸 리더/사용자에게 알려야 한다(단, 이 프로젝트는
사용자가 명시적으로 "커밋해줘"라고 할 때만 커밋하는 것이 확립된 관례이므로, 자동으로 커밋하지
않는다).

## 핵심 규칙: 역사적 기록은 다시 쓰지 않는다

`project_architecture.md`/`project_guidebook.md`의 변경 이력 목록과 회고록의 기존 섹션은
그 시점에 실제로 있었던 일의 기록이다. 지금 사실과 어긋나 보여도 **지우거나 고치지 말고**:
- "현재 상태"를 설명하는 섹션(노드 테이블, 디렉토리 구조, 아키텍처 다이어그램)만 최신으로 갱신
- 변경 이력 목록에는 **새 항목을 추가**(`- (해결됨, YYYY-MM-DD) ...` 형식)

예시 (project_architecture.md의 실제 관례):
```markdown
- (해결됨, 2026-07-25) `target_course`가 course_name과 완전 일치하지 않으면 검색이 죽던
  버그를 fail-soft 필터로 교체(위 `retriever` 행 참고)
```

## 개명/병합된 것을 언급할 때

이 프로젝트는 노드가 여러 번 개명·병합됐다(`docent_generator`+`report_finalizer`→
`report_generator`, `info_lookup_node`→`quick_responder_node` 등). 과거 이름이 등장하는 문맥
(변경 이력, 회고록)에서는 지우지 말고 `(당시 이름 X)`로 표기해 연속성을 유지한다:

```markdown
`report_generator`(2026-07-24 이전엔 `docent_generator`(당시 이름) 두 노드였음 — 통합됨)
```

단, **현재 상태를 설명하는 섹션**(노드 테이블, 지금 무엇이 어떻게 동작하는지)에 옛 이름이
그대로 남아있으면 그건 단순 stale reference이므로 바로 정정한다 — 역사적 기록과 현재 서술을
혼동하지 마라.

## 회고록 작성 규칙

당일 회고록 파일(`docs/retrospectives/{오늘 날짜}.md`)이 이미 존재하면 **새 파일을 만들지
말고 새 섹션으로 append**한다(예: 다른 작업 세션이 이미 같은 날 회고를 작성해뒀을 수 있음).
기존 내용과 저자 표기가 다르면(예: 다른 페어 프로그래밍 도구로 작성됨) 그 사실을 존중하고,
자신의 작업분은 별도로 구분되는 새 섹션(`## N. 후속 세션 — ...`)으로 추가한다.

회고록 구조 관례: `0. 배경` → `1. 진행한 내용` (번호 매긴 하위 섹션) → `2. 잘된 점 및 배운 점`
→ `3. 남은 작업 및 향후 계획`.

## CLAUDE.md 갱신 시 특히 주의

- 이 파일에만 있는 필드/메커니즘 설명이 실제 코드와 다르면(예: 특정 필드를 "죽었다"고
  서술했는데 실제로는 재사용 중), 반드시 관련 코드를 직접 다시 읽고 확인한 뒤 정정한다 —
  문서를 보고 문서를 고치면 같은 오류가 반복된다.
- "Harness / safety gates" 섹션의 Gate A~E 규칙, 도메인 로직 규칙(하드 제약 불변 등)은 이
  프로젝트의 최상위 정책이다. 코드가 이 규칙과 어긋나게 바뀌었다면, 문서가 아니라 어느 쪽이
  실수인지부터 사용자/리더에게 확인한다.

## 파일 링크 규칙 (CLAUDE.md 자체 규칙, 모든 문서에 적용 권장)

- 실제로 존재하는 경로만 링크하고 확장자를 정확히 쓴다.
- 마크다운 링크 뒤에 한글 조사(은/는/이/가/을/를/의/에 등)가 바로 오면 링크가 깨지므로, 닫는
  `)` 뒤에 공백을 하나 넣는다.
